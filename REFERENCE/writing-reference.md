# Si2C 写作参考

只在需要实例、术语处理、证据打包、信息状态、改稿核对或结构选择时读取本文件。引号与代码块中的反例受“反例豁免”保护：它们用于展示问题，因此可能故意违反 Si2C 规则。

示例改编自技能作者处理过的真实案例，已脱敏：内部标识符替换为占位或通用词，不影响判据理解。

## before/after 示例

### 自包含：从动作清单补成决策链

**案例背景**

一篇案例复盘：主分析 agent 在排查 DDS 数据读取错位故障时，为何主动检索 Git 历史。rollout 是 agent 的完整运行记录；“一拍错位”指每次读到上一条数据。

引文见 SKILL“示例：补全决策因果链（已脱敏）”。

**差异分析**

Before 只列材料和阶段结论。读者看不到每个动作要验证什么，也不知道结论如何从材料推出。

After 补出观察、验证目标、方法、结果和下一问。逐字内部动机不可得，工具序列只能支持“推导”。原稿仍残留 creator、rollout、commentary 等过程词；这里只学习因果链结构，不学习用词。

### focus：删除真实但无关的会话关系

**Before 摘录（已脱敏）**

> “### 第一步：对齐对象——「后者」其实是子会话”
>
> `第1行 "title":"故障排查示例","source":"user"`
>
> `第2行 "parentSession":"<父会话ID>"`
>
> “前 5185 条记录与 `<父会话ID>` 的条目 id 逐条相同。”

**After**

用户编辑稿给整节加了删除线，但没有重编号。重写稿才彻底删除该节，直接从“排查外部暗示”开始。

这些内容描述会话的父子或分叉关系。它们真实，却不帮助回答文档的核心问题，所以应删除，而不是换成更温和的说法。

### 证据边界：不要声称知道不可见的推理

原文区分三类内容：

1. 工具行动能够反推的排查分支；
2. 模型在可见输出中明确形成的方向；
3. 复盘时补充的控制假设。

内部 reasoning（内部推理记录）是密文，不能断言模型采用过复盘者后来命名的 A/B/C 标签。可迁移的做法是保留证据来源差异，而不是照搬长标签。

## 改稿与回读验证

改稿先读现稿，圈定本次授权范围。只调整相关章节，其他人工修改保持原样。自检和删改只作用于授权范围；范围外发现的问题列为建议，不直接改动。

- **联动核对**：字段、示例、流程、状态或验证有一处变化时，检查其余引用。例如字段从 `requestId` 改为 `traceId`，接口表、流程图和验收场景要同步更新。
- **清理已解问题**：用户或评审者已经补齐的事实或决定，应写入相应结论，不再留在“待确认”或“未定论”。例如回滚条件已有正式记录，就从问题清单移除。
- **保护外部版本**：写回前记录可比较的版本信息。若远端基线已变化，先识别新增差异，再合并授权范围；不要整篇覆盖。
- **回读真实结构**：写入成功只表示请求被接受。回读时检查标题层级、列表结构、表格列数及代码块换行。例如三列表格写回后仍应保持三列。
- **说明验证边界**：只能读取文档结构时，写明结构已核对、可见样式未验证。不要把接口成功当成内容已验收。
- **发布前脱敏（标识符）**：工作底稿转为可发布文章时，把内部标识符替换为占位或通用词。内部标识符包括工单号、产品或项目名、内部路径与文件名。还包括会话与评论 ID、内部证据代号和内部链接。人员与设备标识也要脱敏，如人名、花名、账号、路径中的用户名、车辆 VIN 和设备序列号。正文用角色或职责称呼人员。例如，把路径中的用户名替换为 `<用户>`，把具体姓名改为“值班工程师”。公开领域术语和公开可查的外部引用保留；只在组织内部可见的引用同样脱敏。
- **发布前脱敏（真实性声明）**：脱敏后同步修正“逐字原文”“真实示例”等真实性声明。例如把工单号改为 `bug-XXXXXXX`，并将标题改为“示例（已脱敏）”。

## 证据打包

正文先写判断，再给足以复核该判断的最小证据。证据长度取决于用途：

1. **完整语义单元按决定性程度保留**：任务指令、配置等若直接支撑核心论断，即使长也完整给出。证明“不存在”或“没有差异”时，也应完整给出相关语义单元。长度只决定放在正文、折叠块或附录，不决定能否裁剪。复现所需的短命令也完整给一次；后文交叉引用，不重复粘贴。会改变系统状态的命令还要写明影响范围、隔离前提和恢复方法。例如，修改系统时间只在测试机执行，并给出恢复时间的命令。
2. **可裁剪的观测材料只摘决定性片段**：日志、堆栈和只需局部判断的代码保留连续上下文，标出文件、时间、行号或帧号。可以写“中间省略 3000 行重复栈帧”，但不能删掉证明重复模式所需的相邻帧。完整原件放折叠块或附件。摘录可以截断并标明省略，但不能改写片段内的字符、转义、标点或原有省略号；源材料本身不完整时逐字保留并说明缺口。
3. **让读者看见差异与编号含义**：数量、状态、时序或性能是关键时，用小表写“预期、实际、含义”。正文引用自造的一组编号（如未定论 U1–U4、方案一/二）时，先用小表集中定义“编号、内容、备注”，再在正文引用。不要让读者从原始输出或分散句子中自行整理。引用多源日志前，用小表列出“标识、角色、运行批次”。进程重启后重新对应标识。时间统一到同一时区，或说明换算关系；进制和单位也要标明。例如，注明 `0x1a2b` 与十进制 `6699` 是同一服务标识。
4. **图像不是唯一载体**：截图、时序图和颜色旁写出文本结论与决定性值。图片失效或转成纯文本后，核心判断仍应成立。
5. **评价性数字要有参照和含义**：用于说明结果或趋势时，给出目标、改前值、同版本或其他可比基准。没有可比基准时写明缺失，不要补造。时间戳、错误码和配置值不强行对标。数字后说明它改变了谁的哪项工作或哪个判断；例如“复核耗时从 3 天降到 4 小时，值班工程师可在当班完成”。结果段每写完一个判断，都追问“这会改变什么（So What）”；答不出就删。性能或检测数值要写明工具、采样窗口或次数、统计口径和负载条件。工具存在假阴性或精度限制时，结论旁说明局限并缩小适用范围。例如，CPU 占用率要注明采样时长，不能只引用单张截图。
6. **把日志缺失当作证据前核对条件**：写明该日志的打印条件和现有日志覆盖窗口。打印条件包括日志级别、启动期、首次或周期打印。两项任一不明时，结论写成“未定论”。例如，只有启动时打印的日志不能用运行期片段证明功能未执行。
7. **外部说法与实测分开**：标准、官方文档、上游 issue 或源码等可定位的权威来源可以作为证据，但要标出处；转述、经验、博客和模型背景知识在验证前只算线索。与实测冲突时，并列写出原说法、原始输出和所测版本。依赖缺陷还要列出受影响版本区间、本项目版本和上游修复版本。例如，报告应写“组件 2.30 修复，本项目仍使用 2.27”，不能只贴上游链接。

根因报告优先形成三环：

- **现象证据**：证明故障确实发生，以及发生在哪个对象和范围。由用户反馈触发时，还要用时间、调用关系或界面与接口对应证实技术异常；证据不足就标为“推导”。例如，不能只并列“界面失效”和“进程退出”，要给出调用关系或时间对齐。
- **机制证据**：解释所声称的根因机制怎样产生观察到的现象。先写本应成立的约束，再写破坏该约束的时序或路径；修复说明恢复了哪条约束。例如，回调对象的生命周期应覆盖回调执行。
- **验证证据**：通过复现、反证、故障注入或修复后对照区分替代解释。
  - **复现锚点**：写明代码版本、触发命令或步骤，以及复现率。偶发问题优先写成 N/M。
  - **同条件对照**：在相同触发条件下比较未修复版和修复版，分别报告次数与结果，并补回归检查。例如，报告“未修复版 15/20 崩溃、修复版 0/20 崩溃”，并用相同命令回归。
  - **运行边界**：列出为复现加入的等待、调试宏、编译选项或环境变化，并说明它们为何不影响结论。写明与现场一致的堆栈、日志序列或计数，结论只覆盖已验证环境。例如，加等待放大竞态时，要说明不加等待也能低概率复现，或复现堆栈与现场一致。
  - **证据批次**：标明日志或截图来自现场、复现第几次或修复后哪次运行。混用不同批次时，说明会变化的值。

三环未闭合时，按已有证据写成“推导”“推测”或“未定论”，并说明缺哪一环。三环闭合时可写成“已验证的推导”，不改称“实证”。

## 信息状态

事实的可信度用证据等级标注；信息状态只用于方案、决定、范围和行动项。信息状态写进句子，不另设方括号标签。

- **已确认**：有正式决定或评审记录。例如正式评审记录明确采用异步接口。
- **提议**：仍在比较的选项。例如“改用异步接口”尚未形成决定。
- **设计假设**：为方案暂定的前提，同时写明验证方式。前提本身是否成立，用证据等级标注。例如先假设调用方支持幂等键，再核对接口契约。
- **待确认**：缺少决定或责任归属，并说明它影响什么。例如重试上限未定，会影响超时预算。

事实缺口使用“未定论”或“不可得”，不归入信息状态。

提问不代表承诺，摘要也不代表正式决定。例如“是否改成异步接口？”仍是提议或待确认；会议摘要只能作为查找线索，正式决定应回到原始记录核对。

## 黑话处理表

先问：读者理解当前结论是否需要知道该机制？再选择删除、改写或首次解释。

| 类别 | 例子 | 默认处理 | 可以保留的条件 |
|---|---|---|---|
| agent 工作流内部标记 | `NEEDS-INPUT`、marker、done、node id | 删除 | 真实缺口改写为“未定论”或“尚缺资料” |
| 稿件轮次 | r1/r2、round、supplement | 删除 | 修订史是研究对象时放到版本说明 |
| 编排动作 | 派单、lane、node、编排轮次 | 删除 | 独立性影响可信度时改写为“另一分析独立复核” |
| 裁决标记 | verdict、PASS、scorecard | 改写实际结论 | 读者必须审计评审流程时首次解释 |
| 证据来源缩写 | `S1:`、`S2:` 等作者自造的证据文件代号 | 展开或删除 | 多次使用且确实节省阅读成本时首次定义 |
| 取证坐标 | Event 234、rollout L298 | 正文概述事实，坐标放附件 | 坐标能定位已提供的附件 |
| 内部角色 | creator、critic、runner | 换成读者熟悉的说法：worker、reviewer、agent；或首次定义 | 角色归属就是研究问题时首次定义 |
| 技术证据 | 函数名、命令、错误码、地址、路径 | 保留原值 | 始终保留，并按受众解释作用 |
| 领域缩写 | DDS、UAF、DWARF | 首次解释 | 受众明确共享该知识时可省略 |
| 组织黑话 | 赋能、抓手、闭环、拉通、对齐、颗粒度、沉淀、打法、链路、心智、兜底、卡点、底座、生态、基座、工程化、中台、兑现、势能、落地、第二曲线、动能、飞轮、非对称优势 | 检查后删除或具体化 | 指向读者熟知的正式概念时 |
| 夸张比喻 | 重塑边界、量子纠缠式比喻、范式颠覆、深刻变革 | 改为实际变化和适用范围 | 引用原文或类比确实解释机制时 |
| 程度副词 | 显著、大幅、明显地、极大地 | 换成数值、阈值或具体影响 | 统计学术语有定义，或来源只能定性描述时 |
| 正文 emoji 强调 | 🚀、🔥、⚡️ 等 | 删除装饰性符号，直接写结论 | 状态图例有明确定义，或受保护引文中原样出现 |
| 情绪化故障动词 | 崩盘、踩空、失血、溃败、彻底崩了 | 改成可观测状态和范围 | 真实崩溃事件、错误码、日志或受保护引文保留原值 |
| 清嗓套话 | 值得注意的是、众所周知、综上所述、总而言之、不难发现 | 删除 | 承担必要结构提示时 |
| 抽象评价 | 全面、深度、系统性、强大、稳健、丝滑、无缝、至关重要、复杂微妙、深入探索、富有洞见 | 用具体对象、动作、范围或证据替换 | 后文立即给出可验证标准 |
| 连接词 | 此外、与此同时、因此、从而、进而 | 核对逻辑 | 句间确有并列、时间或因果关系 |

词表是复核触发器，不是禁用表。“链路”可以指已定义的请求链路；“从而”可以连接已证明的因果。真实进程崩溃也应准确写成“崩溃”。不能只因命中词表就改写。

## 文体模板

### 主模板：技术调查、故障分析或排查复盘

适合回答“发生了什么、为什么发生、证据是什么”。

1. **背景与结论**
   - 问题、影响、当前结论和置信度。
2. **证据与范围**
   - 关键日志、代码、转储或实验。
   - 时间、版本、环境和缺失证据。
3. **推导概览**
   - 用 3–7 步概括主线，不罗列工具调用。
4. **分步推导**
   - 标题写本步要回答的问题、判断或验证目标，不要只写对象名。
   - 观察 → 验证目标 → 方法 → 结果 → 下一问。下一问应引出下一节要回答的问题，不复述本节。
   - 事件时间线按真实时间；诊断分析按证据依赖，可以从症状正推，也可以从缺失结果倒推。
5. **补充说明与行动**
   - 替代解释、未定论、复核入口和后续行动。
   - 方案或修复建议写明代价、影响面和未覆盖场景。例如新缓存只覆盖读请求，就说明写请求仍走原路径。
   - 根因未闭合时，把建议标为规避或缓解，并写明针对的候选原因和验证信号。存在备选方案时，写明切换条件。例如，只调整线程时序时先标为缓解；问题仍出现时，转用恢复生命周期约束的方案。

短报告可以把第 2、3 部分并入第 1、4 部分。不要在末尾重复已经写清的结论。

### 变体：事故复盘

保留主模板的结论、证据、推导和行动。按事故读者的需要做以下调整：

- “背景与结论”增加影响范围和当前恢复状态。
- “证据与范围”可加入检测、响应和恢复时间线。
- “分步推导”突出直接原因、系统性因素和促成条件。
- “补充说明与行动”区分已完成、计划中和待验证的行动项。

时间线只保留改变系统状态、判断或响应的事件。

### 变体：方法复盘

保留主模板，但把“分步推导”集中于关键转折：

- 起始证据与约束；
- 哪个观察改变了验证目标；
- 哪种方法有效，以及证据是什么；
- 失败路径为何失败，仅保留会改变后续方法的失败；
- 方法边界和下次行动。

被推翻的假设压成“已排除：假设；依据”。不要保留大段删除线、按日进度或“补充/修正”等编辑历史。不要按 Event 编号或命令顺序复述全过程。按“决策为何改变”组织内容。

## 严重度说明

### P0：可信度杀手

立即修复：

- 编造事实、数字、来源、体验或意图；
- 无来源的“专家认为”“普遍认为”；
- 把推测写成实证，把相关写成因果；
- 知识截止声明（如“截至我的训练数据……”）或隐藏证据边界；
- “希望这能帮到你”“这是个好问题”等聊天残留；
- 对常规事实做“里程碑式”“意义重大”等无证据拔高。

### P1：理解障碍和明显机器痕迹

发布前修复：

- 外链、截图或颜色代替核心解释；
- 可裁剪的观测材料未裁出决定性片段，或把直接支撑论断的完整语义单元裁成了概括；
- 术语未定义、代词指向不明；
- 决策只有方法，没有观察、验证目标、结果或下一问；
- agent 工作流内部术语、轮次或 Event 编号泄漏；
- 套话聚集、抽象评价；
- 删去修饰性的 AI、Agent、大模型等热词后，若只剩“工具能做”而答不出原技术问题，补具体过程、验证和取舍，或删除无关热词。研究对象本身是 AI 系统时，测试删的是热词修饰，不是研究对象；
- 概念堆砌却没有代码、实测或决策；
- 只贴命令输出，不解释它支持哪个判断；
- 把规范逐条扩写成报告，却没有新增证据或结论；
- 标题硬贴热词，正文研究问题与该技术无关；
- 叠用“可能”“或许”“在一定程度上”等保留语气；
- 无关章节或重复结论；
- 句子单独成立，段落却没有新增判断、证据、细节或推理推进；
- 删除线旧方案、按日进度、“待补”等中间状态残留；
- 结论、正文、示例或表格之间的数值、状态不一致；
- “上一版”“见 r1”等悬空引用。

### P2：风格打磨

有时间再修：

- 句式和段落节奏机械；
- 过渡词过多；
- 感叹号或层级过多；
- 连续用破折号做解释、补充或转折：改用冒号、括号或拆句；
- 抽象的否定转折或递进句套用固定模板：直接写模块、动作和结论，具体对比、纠正常见误解的否定和事实否定不受影响；
- 没有真实三项时，为了节奏补齐三点或三连形容词；
- 列表或粗体成为默认节奏：步骤、字段和检查项适合列表，连续推理改成段落。行内粗体只标关键条件或结论，小标题和条目开头的标签不受此限；
- 按英文语序组句，名词堆叠而动词少：前置主体和动作，负向定义能直说时改成正面判断；
- 可进一步拆分的长句；
- 标题或列表格式不一致。
